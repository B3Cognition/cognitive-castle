#### Important (Should Fix)

1. **A successful append can exceed the frozen batch-receipt ceiling and make its own replay fail.** `cognitive_castle/bulk_exact_store.py:730` checks `max_batch_receipts` only while scanning existing rows for an owner proof. `:430` always appends a new batch receipt, but `:758` reserves only rows/fragments/versions/artifact bytes and `:797` postchecks those same categories; neither accounts for the resulting receipt count. For example, after one staging receipt with `max_batch_receipts=1`, finalization accepts the existing one receipt, appends receipt two and returns `ok` if the other envelopes fit. Its identical final-batch replay scans that second receipt and returns `corrupt`. Stage-only calls can cross the ceiling without even running the scan. This violates the dedicated qualification and preflight resulting-geometry contract. Track/validate the bounded existing receipt count for every mutating operation and charge the new receipt before append; refuse before mutation when the resulting count exceeds the frozen maximum. Add a pure boundary regression and a focused supervised native case covering refusal with unchanged files, plus success/replay when exactly the permitted resulting count fits.

2. **The reconciliation pair grants a new write at the after-state.** `cognitive_castle/bulk_owner_stream.py:259` validates two consecutive states, and `cognitive_castle/bulk_exact_store.py:666` admits either state identically. Both `:758` and `:818` then allow a fresh append/index operation starting from the second state. Thus, after the original write reached the registered after-state, a request with a new batch ID (even just another finalization receipt for the same owner) or another maintenance call can mutate it again. The inherited receipt lookup only prevents this for the identical already-recorded batch; it does not constrain a new request. The root's binding clarification confirms that this pair is lost-reply reconciliation only, not a second write authorization. Preserve actual inherited replay at the after-state, but reject mutation from that state before append or index creation; maintenance reconciliation also needs an explicit non-mutating verification outcome rather than another index build. Add focused pure checks for both mutators and a supervised case showing identical original replay succeeds unchanged while a new batch/maintenance at the after-state refuses unchanged.

3. **The native fixture widens the read budget to 3 seconds.** `tests/test_lance_owner_stream.py:185` and `:186` unconditionally pass a 3-second relative/absolute deadline, including the ordinary `read_sources` call in the finalization test and `bulk_owner` call in the maintenance test. The reported read elapsed times are below 2 seconds, but those calls were guarded with the wrong allowed budget. Select the proper fixed budget by operation and use it for both deadlines. Add an engine-free assertion of the supervisor arguments for the two reads and ordered writes/maintenance; qualify the affected native reads under the unchanged 2-second guard when the root next grants their focused scope.
