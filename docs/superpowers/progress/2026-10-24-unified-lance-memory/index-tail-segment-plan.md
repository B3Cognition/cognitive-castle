Prepared 2026-10-25. **Read-only preparation only. No native call, fixture copy, executable, product change or matrix resumption was performed.** The preserved original fixture remains untouched. Root owns any later authorization and native slot; the SQLite source agent currently owns native work.

## Decision

Lance 4.0.1 can represent multiple same-name index metadata entries and preserve an old UUID during an explicit `CreateIndex` publication. That does **not** establish usable disjoint BTREE query segments: the pinned scalar executor selects and opens one matching UUID, and reports that selected metadata entry's fragment bitmap. The proposed fragment-only strategy therefore lacks a clear supported end-to-end query contract. Do not prepare an executable that calls its aggregate metadata coverage fully indexed or qualifies its lookups merely because an unindexed scan returns correct rows.

The earlier `optimize_indices(...,num_indices_to_merge=0)` result is explained by pinned native source, without another storage experiment. Its scalar branch creates a new UUID, includes old coverage and calls BTREE update; the numeric merge option reaches the vector branch instead. BTREE update combines old index entries with the new-data stream and writes a newly trained physical index. This is a **derived whole-index replacement**, not the disproven old-segment-preservation contract. [Scalar optimization](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance/src/index/append.rs#L161), [BTREE update](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance-index/src/scalar/btree.rs#L1669).

Atomic, crash-safe replacement of a **derived index** is not inherently prohibited by the canonical append-only promise. It must preserve canonical text, provenance, rows, data fragments and durable receipts, publish through an atomic manifest change, retain the prior readable state on pre-publication failure, and meet unchanged resource/disk/recovery requirements. Destroying originals to rebuild them remains prohibited. The 65,536-ID initial-build and replacement-call measurements support only their recorded fixture conditions; larger cardinalities, real bulk fragment counts, retained-version growth and crash/replay behavior are unqualified. The product 16,384-row gate remains unchanged. No segment design is required merely to avoid calling legitimate derived replacement by its accurate name.

## Exact query and coverage boundary

There are three different notions of coverage; do not conflate them:

1. Candidate `bulk_exact_store.coverage()` unions all described segment bitmaps; that would call old+tail metadata fully covered.
2. Native `unindexed_fragments(name)` also unions named metadata entries (`rust/lance/src/index.rs:1844–1858`). This does not prove which scalar entries a query executes.
3. Scalar query execution calls `load_scalar_index(...with_name(...))`, which iterates metadata and returns one matching entry (`index.rs:869–927`). `ScalarIndexLoader::load_index` opens only its UUID (`io/exec/scalar_index.rs:57–70`). `fragments_covered_by_index_query` returns that one entry's bitmap (`:119–150`). `open_scalar_index` opens the requested UUID, without a same-name segment union (`index.rs:1407–1442`). These paths provide no basis for claiming that both disjoint BTREEs are queried. Correct tail results may come from residual fragment scans.

An additional boundary: Python `Index` extraction sets native `index_details=None`, even if other fields are supplied (`python/src/transaction.rs:61–99`). `index_matches_criteria` can reject missing details when multiple indices share a field (`index/scalar.rs:501–514`). Do not add an ignored Python attribute, synthesize a details protobuf, bypass `_ds`, mutate manifests, or switch to vector-only builders to evade this. The precise result may depend on entry selection and inferred metadata; it is not a verified multi-BTREE contract.

[Native aggregate coverage](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance/src/index.rs#L1844), [single scalar loader and query coverage](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance/src/io/exec/scalar_index.rs#L57), [Python metadata conversion](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/python/src/transaction.rs#L61), [criteria guard](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance/src/index/scalar.rs#L501).

## Stale publication, crash and orphan obligations

`read_version` is transaction provenance/conflict input, not a guaranteed strict compare-and-swap. CommitBuilder may load current state and reconcile transactions. Exposing `max_retries=0` prevents asking for the default20 retries but must not be described as a stale-state CAS. Require a fresh version/index/fragment/hash precheck under the private writer lock and global admission immediately before publication; stale state means refusal, not rebinding or broadened coverage. A production route would additionally need focused evidence for actual conflicting index creation/append/compaction races. [Commit API](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/python/python/lance/dataset.py#L3594), [native commit configuration/current-state loading](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance/src/dataset/write/commit.rs#L152).

Before publication, a stopped build/merge can leave orphan files while the old index and bounded unindexed tail remain readable. Never acknowledge coverage from file existence. After a lost commit acknowledgement, reopen read-only and check the exact intended UUID/version/coverage; never repeat a build into a partial UUID directory or assume failure implies rollback. Account for orphan plus retained old-index bytes. Preserve the current fixture on any ambiguous result; no opportunistic deletion or automatic cleanup. A later narrowly reviewed cleanup may remove only proven unreachable derived files while respecting pinned versions/readers. This minimal experiment would not by itself qualify crash recovery, conflict replay, sustained accumulation or compaction/remapping.
