## Concrete execution and retry paths

- `memory_coordinator.py:524-562`: `_tick` starts a five-second wall clock; each `run` passes only the remaining budget into `run_memory`. `finish` retains prior counters even when the last operation fails, then atomically saves scheduler progress and the last receipt. Thus a final unavailable status does not undo the earlier successful slice or queue registrations.
- `memory_runtime.py:180-231,315-430`: the operation deadline is `min(operation deadline, remaining tick budget)`; `capture_one` has a three-second operation cap (`:29-44`). Admission can wait up to 0.5 seconds before `memory_busy`. `_supervise` returns `worker_deadline` when the allotted worker time expires, then kills/reaps its process group in `finally`. Worker setup, supervision and teardown contribute overhead, so 5.1024 seconds is compatible with a five-second work budget rather than evidence of an unbounded worker. No worker exception is needed to explain the receipt.
- `memory_coordinator.py:320-381`: spool metadata is claimed, then `queue_source` commits registration before priority is atomically persisted and the claimed event is acknowledged. Refusal before acknowledgment leaves claimed metadata for replay; committed priority survives acknowledgment. Replays are idempotent. `queued_sources=16` means sixteen successful enrollments/discoveries in that tick, not sixteen new complete sources or a global backlog count.
- `memory_coordinator.py:31-32,435-466,470-502,570-635`: persisted turns rotate spool/fresh/ordinary/fresh/discovery opportunities. Fresh keys are rotated before work and retained on `worker_deadline`; waiting/attempted sets are per tick. Ordinary queue pagination includes `pending` and `failed` sources (`memory_capture.py:316-334`) and wraps after the cursor reaches the end. Its cursor advances before the attempt, so a failed ordinary source is retried after the next wrap, rather than permanently removed. Discovery reservation is persisted independently of lane turns. Worker failure ends this tick, with the next opportunity already saved.
- `memory_capture.py:247-315`: `capture_one` prepares a durable scope watermark, invokes ingest, then updates queue accounting/state and scope mapping. A supervisor kill does not necessarily execute the `state='failed'` update; `failed_sources=1` in the coordinator receipt is a failed invocation count, not proof that a durable source row transitioned to failed. An existing pending/failed row remains eligible. Scope recovery replays a previous `scope_attempt` against the durable checkpoint before starting a new attempt (`:223-241`), covering ingest committed before scope finalization.
- `memory_ingest.py:176-235,323-406,431-445`: ingest itself aims for a 250 ms slice, reserves the source generation before text writes, saves a write-attempt observation, commits each piece with a deterministic source/generation/record/block/piece request identity, and checkpoints the pending block cursor after each piece. Full-record offset advances only after processing the record. An interrupted worker resumes the last committed cursor/offset; if killed after a piece commits but before its checkpoint, the same request identity returns its existing receipt (`fast_memory.py:222-292`). Replaying does not require dropping the source or advancing past unstored text.
- `fast_memory.py:112-183,557-582`: write contexts use SQLite transactions and rollback-journal mode, commit on successful exit, and save checkpoint plus coverage observations in one transaction. A kill can lose uncommitted work, while committed earlier pieces/checkpoints remain. A receipt alone cannot identify which boundary the worker reached.

## Remaining risk and interpretation limits

No static lost-checkpoint path was identified for an ordinary supervisor deadline. Eventual progress remains conditional: repeated admission pressure, filesystem/SQLite latency, quota/corruption/source errors, or repeated deadlines before the next durable checkpoint can indefinitely delay a particular source. Fair lane scheduling prevents one lane from owning every restart but cannot guarantee successful work within a fixed budget. A single successful slice establishes a completed ingest invocation, potentially with pending bytes, not complete capture.

The current receipt schema omits failed operation, allotted remaining budget, per-source checkpoint before/after, and accumulated refusal streak. Therefore `capture-last.json` alone cannot distinguish an undersized final worker window from a full three-second source stall, or establish sustained per-source progress. Source queue summaries may also lag committed ingest progress when the worker dies between ingest/checkpoint and queue/scope finalization; retry is the recovery path.
