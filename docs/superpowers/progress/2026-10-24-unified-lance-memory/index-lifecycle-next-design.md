# Task 3c: bulk geometry and bounded index lifecycle

2026-10-25. Read-only design addendum; no code, native execution, deletion, product change or new profile. Builds on [index-maintenance-next-design.md](index-maintenance-next-design.md) and the actual [six-case result](index-update-262144-results.md).

The measured supported operation is one existing-index update at 262,144 base rows plus 1,024 new rows/one fragment: 0.7626 s, sampled task/aggregate RSS 198,639,616/224,526,336 bytes. It published a whole new derived output, preserved canonical files and the prior index, and passed fresh/pinned metadata and bounded lookup checks. The task margin was only 2,686,976 bytes. The result does not cover product-expanded row/fragment geometry, repeated cycles, cleanup, a million-row corpus or an initial large sort. Current product integration cannot yet sustain that path: it exposes only full `create_scalar_index` below 16,384 rows, not the qualified explicit update route.

## Physical admission precedes append

Current [import_batch](../../../cognitive_castle/bulk_exact_store.py) at lines 346–438 checks *existing* coverage, then appends `pending candidates + batch receipt`. It does not reserve the resulting tail. An existing tail at 1,024 rows or 32 fragments can therefore accept another write and leave subsequent reads refusing `index_required`. Commit acknowledgment is not a usable-read guarantee.

Reserve under the same writer lock against the opened version, before the native append:

- Exact new rows are `len(pending) + 1`, including new records, field pages, membership pages, owner manifests, optional legacy live receipts and the batch receipt, after collision/replay checks. Existing matching receipts return without appending. Nominal owner/record counts are insufficient.
- A conservative prelookup reservation can count every distinct candidate plus the batch receipt; exact pending counts may later reduce it. Batch validation permits 256 entries/finalizations together, and each finalization can add a legacy receipt, so the general conservative row ceiling is 513, not 256. The current one-owner export interval has at most 257 rows for an entries-only interval or 258 when a live finalization is included. These are upper bounds, not measured actual sizes.
- Require `tail_rows + reserved_new_rows <= 1024` and `tail_fragments + reserved_new_fragments <= 32`. Native write geometry must have an established upper bound and be checked after commit; `max_rows_per_file=1024` is an output limit, not a promise that separate writes coalesce. Current small writes create separate fragments. Refuse before mutation if no row/fragment/disk headroom remains; a lost acknowledgment requires reconciliation, not a guessed rollback/retry.
- Reserve physical/encoded bytes, next full derived output, spill allowance, manifests/transactions, retained rollback indexes and existing orphan debt within unchanged fixture/run/free-space limits. The 64 MiB tracked DiskManager spill setting is not a universal allocation bound. Do not infer next-output capacity only from remaining tail size.

A new generation can bootstrap its first index while still inside both the small-build envelope and usable unindexed-tail envelope (at most 1,024 rows/32 fragments). The 16K create ceiling is not permission to leave an unreadable 16K unindexed tail. Thereafter a separately admitted explicit maintenance operation can sort the bounded tail and stream-merge old sorted entries into full new output; ordinary reads never build/maintain. This route still requires reviewed product integration and measured growing-output bounds.

## One active ID segment is a correctness invariant

Current `coverage()` (bulk_exact_store.py:19–55) rejects multiple logical descriptions but unions every segment's fragment bitmap in the remaining description. Pinned scalar query loading instead chooses one index metadata UUID and opens that UUID; its deletion mask uses that selected bitmap. The union can consequently claim coverage the selected scalar index does not supply. [Pinned loader, lines 58–70 and 339–346](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance/src/io/exec/scalar_index.rs#L58).

Require one logical `castle_exact_id` BTREE over `id` and exactly one active segment; validate its UUID/descriptor bitmap against live fragments, and calculate the tail from that single bitmap. Reject unexpected multiple active segments instead of granting union coverage. Retained old UUID directories are not active segments. Missing index is acceptable only within the bounded bootstrap tail. Stable-row IDs, deletions and fragment-remap paths remain outside the append-only qualification.

## Fragment and retired-output debt remain gates

`LanceExactStore._paths()` (lines 91–113) recursively lstat-validates **every** retained artifact on every entry, including old manifests/indexes/orphans. `_writer()` does that walk before opening the dataset; `_read()` does it too. It does not read all bodies, but cost grows with artifact count. Coverage also enumerates all fragments, and owner/batch verification performs additional bounded lookups. The six-case pass covered roughly 333 fixture files and 257 fragments, not years of tiny intervals. Indexed fragments remain after updating the BTREE; resetting tail coverage does not reduce fragment count or `_paths` traversal.

The last update added 11,960,320 allocated fixture bytes while retaining the old index pair. Repeating such whole-output writes indefinitely exceeds any fixed disk ceiling even if each new-tail sort stays small. Canonical row/fragment growth also remains. The present design can remain safe by reserving and stopping, but cannot promise indefinite ingestion under these caps. No existing measured retirement/compaction path establishes a sustainable capacity envelope.

Pinned public `cleanup_old_versions(older_than, retain_versions, delete_unverified=False, error_if_tagged_old_versions=True, ...)` is dataset-wide, not a derived-index-only deletion API or dry-run candidate list. Its working set comes from retained manifests, tags and branch lineage; selected old manifests and unreferenced files can be removed. It does not establish application reader/replay leases. Unknown young files receive conservative age protection; forcing unverified deletion requires excluding concurrent updates. [Python API](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/python/python/lance/dataset.py#L2415), [cleanup reachability, lines 131–279](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance/src/dataset/cleanup.rs#L131).

Before any obsolete **derived** output removal, prove the exact committed current generation; the retained/tagged/branch and rollback/replay version set; absence of live consumers needing candidate UUIDs; complete successful manifest/index reachability; no in-progress or unresolved write acknowledgment; and preserved hashes/reachability of every canonical file. An age or replaced UUID alone proves none of those. Current `version=` bulk reads are a latest-version fence returning stale, not a persisted retention lease, and the product has no qualified reader/tag retirement protocol. Dataset-wide cleanup is therefore not an authorized solution here. Canonical text/provenance/pages/memberships/owners/receipts and original archives must remain protected.

Public `optimize.compact_files(...)` merges small fragments and can rewrite canonical data, remove deleted/dropped content and remap indexes (with `defer_index_remap` options). It is not derived-output retirement. Although supported by the engine, no append-only canonical-file-preservation or resource proof makes it acceptable as this task's automatic escape hatch. Do not invoke it or delete originals. [Pinned compaction API](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/python/python/lance/dataset.py#L5531).

## Smallest next geometry qualification proposed

One later separately frozen experiment should test **one full fragment-limited bulk cycle**, without cleanup, a large initial build or a larger row scale. Use a newly inventoried physical copy of the preserved successful V35 fixture (263,168 rows/257 fragments); freeze current store/codec bytes and unchanged guards/profile. Source validation, COPY and copied BASE precede writes. Build 32 distinct canonical-valid synthetic one-record owners: each has four nonempty one-page fields, one membership page, one bulk record, one owner manifest and one batch receipt, no optional legacy receipt. Each single `import_batch` call writes exactly eight new rows in one fragment. This models actual owner publication rather than raw six-string record-only append.

The fixed sequence is 37 cases: source VALIDATE (read2s), physical COPY (write3s), BASE (read2s), 32 separately supervised owner APPENDs (write3s each), one explicit existing-index UPDATE (write3s), fresh FINAL READ (read2s). Summed stage ceilings are 108 s; external RSS/disk/admission/priority/pressure limits and selected 16/64 MiB private-TMPDIR profile remain unchanged. No execution is authorized by this proposal.

At every append, count all physical rows/fragments and artifacts, prove owner/member/receipt visibility and deterministic replay binding, and include `_paths` and owner verification inside its deadline. After 32 calls expect V67, 263,424 rows/289 fragments and a 256-row/32-fragment tail. The next owner's one-fragment reservation must be identified as inadmissible **without attempting that append**. UPDATE must produce V68 with one active UUID, zero tail, canonical data unchanged and all prior derived files retained. FINAL READ checks representative old/new records, owners, all four page kinds and batch receipts, absent IDs, pinned V67 state, unchanged original inventory and the additional complete derived-output debt. Stop first refusal; no retries, tuning, automatic maintenance, deletion or hidden fragment packing.

A pass would qualify only that one 32-fragment real-bulk tail cycle at this fixture scale. A refusal would locate the next actual gate in this sequence. Neither result closes sustained artifact-walk cost, whole-output time/RSS growth, canonical fragment capacity, safe derived retirement/rollback/replay, or expanded-corpus sizing. Those gates require explicit evidence before migration; no sharding framework or higher caps are inferred.
