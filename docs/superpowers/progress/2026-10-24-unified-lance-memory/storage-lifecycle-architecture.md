# Task 3c storage lifecycle decision support

2026-10-25. Architecture only: source inspection, no engine imports, source-data reads, tests, migration, cleanup or product edits. The source-adapter writer is unaffected. This recommendation requires a root decision and later qualification; it is not a capacity permit.

**Narrowed recommendation: bounded, sequentially allocated canonical Lance partitions, with owner-affine allocation and a metadata-only SQLite ID directory.** Reserve each complete declared owner before its first stage; roll over only between owners. Use a dedicated partition for a known large owner only when its complete geometry and finalization fit a qualified envelope. Coalesce small owners within existing bulk frames, keeping one writable partition at a time. This is a storage boundary for the existing store, not a provider/job framework. No cap is selected here.

Revision after root review: the original proposal was unqualified. Its suggestion to split a new owner's staging across partitions and introduce resumable hash-state/partial-proof machinery is withdrawn. [Task3a brief](task-3a-brief.md) requires ordinary streaming `hashlib` and restart after interruption; [Task3b2a brief](task-3b2a-brief.md) requires full current-tick verification without durable partial-proof phases. The narrower design below preserves those contracts. It targets the actual inventoried corpus plus admitted live owners, not arbitrary unbounded occurrences.

## Why the single-dataset alternative is insufficient

The 262K update proves one bounded-tail merge at one scale, with only about 2.6 MiB task-RSS margin. It does not establish the eventual expanded 519,641-source-row corpus. One owner/interval per append can produce roughly one fragment per small occurrence. `max_rows_per_file=1024` does not merge independent writes. Current `_paths()` walks every retained artifact; `coverage()` visits all fragments; BTREE updates produce an entire new derived index. Small-tail updates reduce sorting, not total output cardinality. Coalescing reduces constants; compaction reduces fragments; retirement reduces obsolete bytes. None bounds the size of the single current index or its future full replacement as live dialogue accumulates.

| Candidate | What it resolves | Remaining structural operation |
| --- | --- | --- |
| One dataset: multi-owner batches, staged compaction, retained-version cleanup | Fewer appends/fragments; obsolete physical-copy debt can be reclaimed after preservation proof | Dataset-wide manifest/index metadata, whole BTREE replacement, index remapping and cleanup reachability still grow with the entire corpus. No supported resumable BTREE merge/commit boundary was established. |
| Bounded Lance partitions plus global ID metadata | Same batching benefit; bounds every native dataset and its replacement/cleanup working set | Global directory grows on disk and needs indexed, paged access; cross-partition identity/publication must be explicit. These are necessary, finite contract changes below. |

For a fixed corpus, option 1 could be qualified at its **actual expanded ceiling**; it is not yet disproven there by measurement. It nevertheless lacks a bounded continuation mechanism for ongoing live growth under unchanged 192/256 MiB, read 2 s/write 3 s and shared 5 s deadlines. Option 2 supplies that mechanism without raising limits or permanently stopping at a corpus-row cap. Finite disk remains real: full-corpus reservations must fit retained originals and rollback plus the new representation.

## Supported API evidence and its limits

All engine claims refer to Lance 4.0.1, commit `5924c97123a25a3e3d500701ef3f158c01f6cd4b`. Existing cached pinned sources and installed Python source were read; missing optimizer/cleanup sources were viewed from that exact official commit.

- BTREE maintenance sorts new fragments and merges their sorted entries with the old index into new output; it is not a persistent set of independently queried BTREE segments. Keep exactly one active ID segment and derive coverage from that segment, not a union of descriptions. [BTREE implementation](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance-index/src/scalar/btree.rs#L1298), [scalar loader](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance/src/io/exec/scalar_index.rs#L58).
- Public `lance.optimize.Compaction.plan`, task `execute`, serialized `RewriteResult`, and `Compaction.commit` support separated rewrite/commit work. The options parser accepts `max_source_fragments`; the high-level `dataset.optimize.compact_files` signature does not expose it. Crucially, Python staged `Compaction.commit` constructs **default** options instead of carrying plan options: do not assume planned `defer_index_remap=True` survives commit. [Binding, including lines 527–533](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/python/src/dataset/optimize.rs#L485).
- Native commit reserves fragment IDs, builds row-address mappings and remaps affected indexes by default. A bounded rewrite task therefore does not prove a bounded overall commit. Limit each planned task's rows/bytes too; fragment count alone cannot bound a large input fragment. Replan after an acknowledged partial commit rather than assuming old task results remain safely committable. [Native compaction](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance/src/dataset/optimize.rs#L1378).
- `cleanup_old_versions` is supported reachability cleanup, not derived-index-only deletion or a dry-run candidate API. It inspects retained manifests/tags/branch dependencies and can remove old manifests, unreferenced canonical-file copies, indexes and transactions. Its age rules are not reader leases. [Public API](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/python/python/lance/dataset.py#L2415), [cleanup implementation](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/rust/lance/src/dataset/cleanup.rs#L131).

## Minimal contract changes

1. **Pack at the coordinator boundary.** Retain existing canonical IDs, owner manifests, page formats, receipt digests, collision rules and source bindings. Existing `import_batch` already accepts multiple finalizations. Gather consecutive intervals from one protected source binding until the existing 256-entry/finalization and encoded/decoded frame ceilings, byte reservation or shared deadline requires a flush. Persist deterministic start/end cursors and input digest, regenerate the identical packed interval on replay, and acknowledge its frontier only after full receipt verification. Do not mix source bindings or store pending bodies in SQLite. Live low-volume writes may remain small; partition admission bounds their fragment overhead.

2. **One owner's new rows stay in one partition; one batch is atomic.** Under the generation writer lock, admit the owner's conservative complete physical expansion, allocate its home partition before its first prepared interval, and retain that binding through finalization/replay. All new canonical records, membership/field pages, owner marker and owner-related receipts remain there. A large owner can span many bounded batches in that partition. Never split a batch; flush a coalesced batch before any next owner that requires rollover. Source bindings remain distinct even if different sources share a partition. Preserve source/owner/canonical IDs unchanged; the home partition is location metadata. An underestimated or unqualified owner remains staged/incomplete without mid-owner rollover, recopying or a success claim.

3. **Global canonical-ID reuse is mandatory.** Add an indexed unique directory keyed by canonical ID, pointing to partition and committed canonical evidence; also route page, owner and receipt IDs. Store only IDs, kinds, hashes, locations, versions, states and counters. Before append, globally resolve candidates in bounded groups; compare actual canonical Lance rows using existing equality/visibility rules. Reuse a matching previously visible record in another partition; reject mismatches and reuse of another owner's uncommitted record. Do not copy it into each new partition or let a local miss mean globally absent. Receipt proofs bind the actual reused canonical row as today, not a fabricated local copy.

4. **Extend the existing prepare/replay/ACK, without proof-progress states.** Add `owner -> home_partition/reservation`, `intent -> destination_partition`, and derived `ID -> partition/kind/hash/publication_state` routes to metadata-only coordination. The prepared intent retains its existing exact cursors, source binding, digest and counts. Under the writer lock, global route resolution supplies bounded remote references to the exact worker; replay regenerates the same source frame and destination, not a newly packed batch. Lance commits rows plus receipt; the existing identical `import_batch` replay checks the full durable proof and expected ID set; owner/live checks and queue ACK still finish in the same 5 s tick. Atomically ACK route updates with the existing frontier/count/reference updates. Stage ACK makes private staging routes usable for subsequent verification, but only final owner ACK exposes its newly owned records; already published reused records remain visible. A final append may occur in an earlier tick, as already permitted, but no partial verification survives a tick.

   Stage routes reference the owning publication gate, so final ACK changes that owner's state and its bounded final-batch routes; it must not update thousands of previously staged record routes at once. Lost responses retain the existing pending interval and its fixed partition. Reconcile that receipt before replay/allocation or route exposure; never treat a directory miss as authoritative absence across unreconciled writes. Source regeneration/replay/owner checks/ACK restart together on retry. The directory can be rebuilt by bounded enumeration of Lance IDs/receipts; missing/incomplete routing refuses rather than scanning all partitions interactively. The existing committed-owner reference gains the partition plus observed version, and existing ACK idempotency prevents double counting. No new phase journal, serialized SHA state, proof accumulator or cross-database atomicity claim is introduced.

5. **Whole-owner verification remains an ordinary bounded streaming attempt.** Preserve original-byte text/membership/field SHA256, exact IDs/offsets/counts/exposure checks and existing final atomic owner/receipt publication. Interruption discards hash state; a later attempt restarts. First qualify the known 52 MiB/6,656-member destination using the ordered scan described below. Repeated deadline failure is a measured gate requiring a separate decision, not authority to persist hash state, skip full replay, increase limits or subdivide original owner identity. Owners exceeding the qualified envelope remain explicitly incomplete; if actual inventory requires one, the full-corpus goal cannot be declared complete.

6. **Reserve complete owners and resulting batches before mutation.** Use protected source summaries to reserve a conservative full owner: records, field/member pages, owner/legacy/batch receipts, fragment/version/artifact growth, intermediate and final index outputs, scratch and orphan debt. Do not take deduplication credit before confirming global reuse. Charge cumulative retained maintenance outputs during the owner, not only its last index. The general current conservative per-batch bound is 513 physical rows, not 256. Enforce `tail + reservation <= 1024 rows/32 fragments` as well as the reserved partition envelope under the same lock; maintenance can occur between staging batches within the same owner. Bootstrap while the tail is readable. Freeze complete-owner/partition envelopes from qualification, never adopt 262K synthetic rows as production allowance. A full partition rolls over before the next owner; an unresolved write or exhausted global reservation does not.

7. **Bound cold reads and validation.** Keep current `_paths()` validation inside the selected, bounded partition; do not recursively validate the entire partition root on every lookup. Validate private root identity and registered partition descriptor directly, then validate that partition's artifacts. Page the global inventory separately. Group directory-selected IDs by partition, bound simultaneously open datasets and returned frame bytes, and use one shared session deadline; multi-partition pages need continuation instead of silently widening fanout. Canonical record hydration must also locate and validate its owner/membership evidence. A descriptor/cache hit never substitutes for row/hash/exposure verification. This avoids introducing a new file-validation trust shortcut merely for speed.

## The known large owner and unavoidable remote references

The known disposable source fixture contains **54,525,952 original text bytes and 6,656 members**. Its corrected SQLite member stream passed at 0.4776 s with 56,377,344/100,532,224 task/aggregate RSS; the successful export slice had no owner finalization. This proves source streaming only. The measured destination whole-hash fixture was only 870,400 text bytes/128 chunks. Neither result qualifies 52 MiB Lance finalization or a complete 5 s replay/ACK tick. [Source evidence](task-3b1-report.md), [destination evidence](task-3a-report.md).

**Supported smaller candidate:** keep the large owner's newly written material in one dedicated pinned partition, preserving the exporter's existing order: descriptor fields, then membership/record pairs, with batch receipts interspersed. Read its bounded fragment span with `scanner(columns=..., fragments=..., scan_in_order=True, strict_batch_size=True)` and bounded batch/readahead/I/O settings. Validate expected owner/field/ordinal/offset at each step, retain only the current page/member/record and ordinary hash accumulators, and include bounded pending final-batch rows in the same verification attempt. Do not sort text or all ID rows, materialize the owner, rely on a hash-ID sort for logical order, or substitute page hashes. The public scanner supports ordered fragment/batch streaming; this is an implementation candidate, not a resource guarantee. [Pinned scanner API](https://github.com/lance-format/lance/blob/5924c97123a25a3e3d500701ef3f158c01f6cd4b/python/python/lance/dataset.py#L680).

Current `_verify_owner` does two indexed fetch groups per 32 members: the 6,656-member case therefore entails **416 member/record lookup groups**, plus descriptor lookups. A sequential dedicated-owner pass can remove that repeated lookup setup for newly stored content. Establish the stream's layout and exact fragment/version binding from committed append metadata; deterministic page IDs, counts and ordinal checks still prove content membership. Initial lifecycle performs no compaction, so physical insertion order is retained; any future rewrite must requalify the stream locator. A bounded fallback scan of the entire selected partition is possible only if that partition's complete scan was qualified. No per-page scattered lookup or corpus-wide scan is assumed necessary for the no-reuse case.

Owner affinity does **not** eliminate global reuse. A later owner can reference an identical canonical record already published in an older partition. Its new membership/scopes/descriptor pages and owner remain local; the canonical record, its first-owner visibility witness and possibly an existing legacy receipt remain at their registered locations. The new batch proof must validate that real remote canonical row; owner hashing must insert its **actual bytes at the required ordinal** through bounded routed fetches. Do not duplicate/rehome it to make the stream contiguous, or reuse a staged foreign record. `lookup_many` candidate checks, `_verify_batch`, `_verify_owner`, `visible_source` and original receipt verification need this bounded resolver; `bulk_owner`/`bulk_page` normally route directly to the owner's home. Cross-partition cold I/O, including reuse scattered over many old partitions, is a distinct qualification gate. A successful no-reuse 52 MiB scan does not cover that distribution.

## Retention and physical maintenance

Logical append-only means every committed user record, canonical ID, provenance value, membership and durable receipt remains readable. It does **not** require every superseded physical encoding or derived index to exist forever. Original archives, protected migration sources and existing SQLite rollback stores remain outside cleanup authority. Native row addresses and fragment filenames are not canonical identity.

The smallest initial partition lifecycle can **seal without compaction or cleanup**, retaining its finite version/index history. Bounding rows, bytes, fragments, versions and artifacts also bounds that amplification per partition. Charge all retained copies in the full-corpus capacity calculation; do not call this free storage. This avoids making unqualified deletion necessary to acknowledge a batch. If that measured total cannot fit, qualify retirement before production, rather than silently assuming it will reclaim space.

For a later reviewed maintenance operation, first prove equality of every rewritten logical row and receipt, then publish a new immutable partition version. Lease actual dataset versions for readers, migration verification, replay reconciliation and rollback checkpoints; current `version=` is only a freshness fence. Protect durable pins with supported tags or conservatively withhold cleanup. Expiration alone cannot release a live reader: require closed/confirmed-reaped supervised workers. Keep replay receipts as canonical rows indefinitely; replay should resolve current identical logical data and need not retain every historical manifest indefinitely.

Only after the exact retained-version set is known, all relevant intents are reconciled, writers are excluded, and original roots are excluded may supported partition-scoped cleanup retire unreachable derived output and **proven redundant** rewritten canonical copies. Do not manually sweep arbitrary Lance files or authorize `delete_unverified=True` by inference. A killed rewrite may leave charged orphan output; a killed commit may have committed; a killed cleanup may have partially retired files. Reconcile actual current/retained reachability and proof state before releasing reservations. The bounded partition is also the recovery/cleanup working-set boundary.

## One smallest falsifying qualification

First freeze the **known 52 MiB destination finalization and cold full replay/ACK** on its admitted dedicated partition using ordinary streaming hashes. Measure source regeneration, all exact work, queue work and their shared deadline, not just scan throughput. A publish-only pass is insufficient; a first append may be retained for a later full verification tick under the existing pending-interval contract. A refusal remains evidence and leaves the owner incomplete. No runtime or cap selection is authorized here.

Once that gate passes and inventory establishes complete-owner envelopes, the smallest lifecycle qualification is **owner-boundary rollover** with actual bulk-format geometry and a metadata-only directory at projected expanded corpus cardinality. Include packed small owners, the admitted dedicated large owner, one reused canonical ID from a sealed partition, conflicting reuse, cold owner/page/absent lookup and lost acknowledgment between Lance commit and route/frontier ACK. No new owner straddles partitions. Demonstrate continued allocation after sealing, measure retained amplification, and reserve all 519,641 source rows plus observed live delta. This tests a known structural boundary rather than another increasing raw-record matrix.

The falsifier is any operation requiring a corpus-wide native open/scan/index replacement, duplicate global ID, partial owner visibility, unrecoverable directory lag, monotonically growing per-partition work after sealing, failed full-corpus storage reservation, or refusal under unchanged guards. Stop at the first failure. If the capacity forecast depends on retirement, that same qualification must include one protected-reader/replay pin, supported cleanup after release, and preserved canonical-row equality; otherwise retirement remains disabled and all copies stay charged. This experiment is proposed, not executed or authorized here.

Unresolved gates: actual destination expansion and complete-owner inventory; known 52 MiB finalization plus full same-tick replay/ACK; ordered pinned-stream correctness/latency; cross-partition reuse distribution; concrete owner/partition envelopes and retained-plus-temporary storage permit; directory cold queries/reconstruction; crash recovery and any later retirement; source snapshot/live delta reconciliation; and lexical/vector retrieval across canonical locations. Unknown or oversized actual owners remain counted pending and prevent full completion. No serialized SHA-state or partial-proof framework is part of this narrowed design.
