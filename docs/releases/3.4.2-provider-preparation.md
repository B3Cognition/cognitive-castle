# Castle 3.4.2 / Prosaic adapter 0.1.0 release preparation

This is release preparation, not a published release. Keep the historical 3.4.1
tag and earlier candidate wheel/checksum evidence unchanged. The worker remains
the complete `cognitive-castle` package; the host adapter is independently
installable as `b3-prosaic-memory-castle` and imports no worker/model packages.

The Lab's default configuration remains disabled. FTS preserves raw ranking by
default, recency is opt-in and dense retrieval is a separate opt-in profile.
Provider reads do not activate SUE, SOAR, the understanding loop, model judging,
capture hooks or generative calls. Current standalone Castle behaviors, including
explicit requirements/article profiles and bounded understanding, are retained.

## Artifact preparation

Use the Lab's artifact-only Castle workflow against an exact committed source.
It builds worker and adapter wheels/sdists once, verifies that rebuilding each
sdist reproduces wheel payloads, checks package metadata and retains SHA-256
digests. Native Linux AMD64/ARM64 jobs consume the same wheels with the unchanged
public SDK train and PostgreSQL 16/18. Their strict six-case acceptance gates
cover frozen Unicode/CRLF snapshots, scope/provenance, source changes, stopped
workers, fresh-process resume, payer attribution and unavailable-memory policy.
Publication requires all four cells and existing regressions to be green.

For clean Runtime-only smoke checks on published Runtime 0.9.7, use:

```sh
python -I scripts/wheel_smoke.py --host-only
```

The default smoke command continues to require model-facing tool capability.
The public Runtime 0.9.7 release supports host snapshots but lacks
`custom_tool_errors_v1` and `ToolExecutionError`. `memory_tools()` deliberately
rejects it. Existing full adapter tool tests use the separately identified
earlier Runtime candidate; those results must not be represented as public-SDK
tool compatibility. A new qualified Runtime release is needed for that API.

## Optional model provisioning

Public package indexes reject direct-URL distribution requirements. Install the
compatible `en_core_web_sm` model explicitly for existing spaCy/NLP features:

```sh
python -m spacy download en_core_web_sm
```

For offline deployment, install an approved compatible model wheel beforehand.
Embedding/cross-encoder weights for dense and legacy retrieval are also explicitly
provisioned; release qualification of FTS must not download or load them during
reads. Removing the model URL adds no hidden runtime installation or fallback.

## Publication checklist

1. Review and merge the prepared changes only after full upstream regression,
   coverage and native enabled-provider qualification succeed on exact source.
2. Select the retained qualified wheels/sdists and checksums; do not rebuild a
   different artifact silently or reuse historical 3.4.1 candidate identities.
3. Verify license/NOTICE contents, rebuilt-sdist equivalence, isolated installed
   ownership and `pip check` for the chosen host/worker environments.
4. Confirm package-index ownership and Trusted Publisher configuration for each
   distribution. The existing `publish.yml` publishes the root worker only;
   it is a live publishing workflow, not a safe qualification command.
5. Obtain explicit publication authorization before creating release tags,
   publishing GitHub releases or dispatching any package upload. Keep model-tool,
   dense-retrieval and live-model claims limited to their separate evidence.
